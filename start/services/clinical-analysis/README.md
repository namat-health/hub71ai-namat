# Clinical analysis persistence

The intake service owns analysis records and spending in the existing PostgreSQL database. It accepts only active, confirmed fictional submissions. No model calls or API keys belong to this service.

Apply `db/004_clinical_analysis.sql` explicitly after the intake, report processing and questionnaire v2 migrations. Fresh local report preview initialization includes it; an existing preview schema needs the additive migration applied separately. There are no automatic request-time migrations. The migration creates no users. When the existing `namat_hackathon_runtime` role is present, it adds SELECT on the five new tables, INSERT on spend/runs/decisions/inventory reviews, and UPDATE only on spend's `actual_micros,settled_at`. PostgreSQL row locks require UPDATE privilege on at least one column of each locked table, so it adds only `UPDATE(created_at)` on the budget and `UPDATE(id)` on existing submissions. Existing report read/lock privileges remain required. For differently named runtime roles, apply those same explicit grants after the migration. The runtime cannot change `limit_micros`, resize reservations, delete spend or rewrite analysis history. Only the migration/operations role should change the cap. The fixed constraint prevents a cap above $20. Migration 004 reserves $5 under allocation ID `4d2d22a0-4339-4a7a-9a50-09d3a76f1505` for the portal repository's durable local fictional evaluation ledger. Production therefore has at most $15 available while local evaluation is capped at $5. Do not remove, expire or settle that allocation until local evaluation is permanently closed and its usage (including uncertain requests) is reconciled; deleting a local ledger must never create a fresh allowance.

The shared API forwards authenticated portal calls to `POST /internal/namat/api/namat-portal/analysis-store`. The public `/api/namat-portal/analysis-store` path is inaccessible. Bodies contain `{operation,input}`. The allowed operations are `reserve`, `settle`, `budget`, `saveRun`, `findRun`, `getRun`, `saveDecision`, `saveInventoryReview`, and `getInventoryReviews`; responses contain `{result}` or a bounded `{error}` code. The portal derives the clinician actor from its authenticated session before sending a decision or inventory review.

`reserve({reservationId,amountMicros})` atomically reserves a conservative upper bound. One dollar is 1,000,000 micros. Parallel reservations lock the same budget row. `settle({reservationId,actualMicros})` reconciles known usage; retries with the same ID and amount are idempotent. Unknown outcomes remain reserved until usage is known. Reservations never expire automatically. A settled reservation must not be used to dispatch another provider call. Actual overspend is recorded honestly and blocks additional reservations. There is no endpoint to reset the budget or erase spend.

`saveRun` takes `id`, `submissionId`, `cacheKey`, `caseFingerprint`, `inputSnapshot`, `analysis`, `metadata`, `evaluatedAt`, and `expiresAt`. Keys/fingerprints are SHA-256 hex strings. The analysis object includes the matching `caseFingerprint`, full plan and grounding. Metadata retains model, prompt, rules, schema, knowledge and usage versions. Runs and decisions are append-only; a retry must use the same run ID and payload. Expiry is capped by submission expiry and seven days from evaluation.

The input snapshot is `{questionnaireVersion,answers,notes,reports:[{reportId,extractionId,reviewRevision}]}` and contains every active cloud report. Saving a run, reading a cached run, and approving a run compare that snapshot against current database records. Submission and report row locks prevent a concurrent questionnaire change or report correction from making an approval silently stale. Unprocessed legacy attachments are rejected. Decisions accept only test IDs in the saved plan, retain the original analysis, and do not send anything to the patient.

`saveInventoryReview({submissionId,reportId,extractionId,reviewRevision,actor})` records that a clinician checked the parsed list accounts for all report test rows. This is separate from approving an interpretation. It binds the exact current extraction and correction revision under a row lock and is immutable. `getInventoryReviews({submissionId})` returns only still-current signatures; any correction invalidates earlier confirmation. The portal includes this state in its context/cache fingerprint. Successful extraction by itself never counts as complete inventory.

Run `node --test tests/clinical-analysis-store.test.mjs` for offline contract checks. For native PostgreSQL constraint and concurrency checks, set `ANALYSIS_TEST_DATABASE_URL` to an explicitly chosen loopback test database and run `node --test tests/clinical-analysis-postgres.test.mjs`. These tests create and remove a random isolated schema. Native checks skip when that variable is absent; unit test success does not imply database integration has been verified.
